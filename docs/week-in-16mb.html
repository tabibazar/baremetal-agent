A Week Inside 16 Megabytes

An AI agent, a fractal renderer, and an animated slice of a four-dimensional cube — all running as single programs with no operating system beneath them, in the smallest machine a cloud will sell. Building them turned up three reproducible platform bugs, one of them serious. This is the account.

github.com/tabibazar/baremetal-agent  ·  github.com/tabibazar/unikernel-c  ·  MIT

A unikernel is an application compiled together with just enough operating system to run, and nothing else — no kernel to log into, no shell, no processes, no filesystem. The hypervisor loads one binary and execution begins in its own main(). BareMetal, by Return Infinity, is one of the few that takes this to its conclusion: the program is the machine.

BareMetal Cloud caps an instance at 16 MiB of RAM. Not a plan tier — the platform maximum; asking for more returns ramMib exceeds the maximum of 16. The whole week was an exercise in what fits, and what the machine does when you lean on it.

The machine, measured against its nearest rival

Only two other cloud platforms run true unikernels; the rest boot a conventional OS inside something small and fast. So the honest comparison is against one of those two — NanoVMs' Nanos — run on one physical host, same C source, same hypervisor family, five runs of everything. Comparing across two clouds measures the clouds.

BareMetal wins the two things it is built to win, decisively: it reaches your code almost as fast as a plain Linux process starts, with a whole virtual machine in between, and it runs where nothing else will boot. It loses on raw throughput. But throughput was not the interesting loss.

The finding: the machine does not always agree with itself

A test called selfcheck computes one fixed modular exponentiation twenty million times. The inputs never change, so a correct machine returns the same answer twenty million times, by construction. Anything else is the machine giving two different answers to the same arithmetic.

BareMetal ran under Firecracker and Nanos under QEMU, so on their own the first rows leave the hypervisor tangled up with the kernel. The third row is the control that cuts the knot: an ordinary Linux guest, booted under the same Firecracker, on the same host, with the same binary at the same optimisation level — changing only the kernel.

It is not only a warning counter. A second test counts primes over a fixed range; every run must return the same count. Five BareMetal runs returned five different counts — 4267876, 4267777, 4267803, 4267888, 4267838 — where Linux and Nanos return 4268930 every single time. The error is one-directional: it only ever undercounts, so the corruption makes the primality test reject genuine primes rather than accept composites. About one result in four thousand is silently wrong.

The fault is narrow. It lives in 64-bit integer modular arithmetic — the __uint128_t multiply-and-divide that gcc lowers to a __udivti3 call. It was not the missing optimisation flag (BareMetal compiles at -O0, but -O0 versus -O2 is only 8% on this workload), not the hypervisor, and not the host. Three explanations eliminated; the mechanism itself still open. Every later experiment that touched a different kind of arithmetic came back clean, which kept tightening the box around that one path.

Why this is the finding that matters

Return Infinity's stated market is quantitative research, compliance, and trading infrastructure — sold on deterministic scheduling. A workload that silently returns a slightly different answer each run, at one in four thousand, is a poor fit for that pitch. The reproducer is sixty lines, no allocation, no I/O, no threads. That makes it a starting point for them, not a complaint.

What got built on top of it

The vehicle for all of this was a Telegram agent that is the unikernel — every reply comes from a 2.9 MB image with no OS. It answers questions about itself by measuring, not asserting: ask how much memory it is using and it reads its own allocator; ask how fast it booted and it reports a cycle-counter measurement taken at startup.

  • self-knowledgemachine facts, live memory use, build contents, a timed HTTPS round-trip, boot timing by CPU cycle counter, usage counted across every restart
  • semantic memorya vector database resident in RAM — every note embedded to 768 dimensions and searched by meaning, no database and no disk underneath, ~5 microseconds a query
  • web & reminderssearch and page-fetch through a host allowlist enforced in C; reminders that survive restarts because there is no disk to lose them to
  • it can drawrenders the Mandelbrot set on request, and a second instance animates a four-dimensional cross-section — both with a PNG encoder written by hand

The memory story is the through-line. The agent began using 640 KB of its 16 MiB — tidy and wasteful in equal measure. The semantic index took it to 10.4 MiB, 63% of the machine, deliberately: a vector database with no database under it, and the whole point was to use the room. None of it costs a byte in the uploaded image, because uninitialised static memory is not stored in the file — the machine simply wakes up with the room already claimed.

One detail that hides in plain sight

The embedding model returns 3072 dimensions and truncates to 768 on request — but a truncated vector is no longer unit length. Its measured norm was 0.59. Cosine similarity over unnormalised vectors ranks longer notes above closer ones, silently and plausibly; you would never catch it from the output. Normalising in code fixed it, and the test now asserts the norm. Guardrails in code, judgement in the prompt.

A method, learned the hard way: measure the thing that is failing

The renderers post their images to Telegram, and for a while they could not. Chasing that failure produced a string of confident wrong answers, each drawn from real data generalised one step too far. The sequence is the lesson, so here it is in order.

  1. "The image is too big. I need to write a compressor."
    Reasoned from a single 787 KB failure. A day of work, confidently planned. Not written — the wall got measured instead, which was the only good decision in the sequence.
  2. "The ceiling is 256 KB."
    A ladder of body sizes said so — but it was measured against our own service, not the one that was failing. The next frame was well under it and failed anyway.
  3. "The ceiling is 16 KB."
    A second ladder, pointed at the right server this time. Better. Then a 5,008-byte frame failed, and no size hypothesis survives that.
  4. The real bug: nine bytes into every PNG there is a zero.
    The probes sent ASCII; the frames are binary. CURLOPT_POSTFIELDS in this port truncates at the first NUL whatever the length says, so every frame failed at every size while ASCII of the same length sailed through. A read callback fixed it in six lines.
  5. "Now the size limit is real."
    With binary fixed, sizes bracketed cleanly — until a 4 KB frame failed where 10 KB had posted, and an identical frame failed two minutes after succeeding.
  6. The transport is intermittent, not bounded.
    Three ladders had been reading a flaky link's noise as a boundary. The honest response to an unreliable link is to retry it and count how often that was needed — which every frame's caption now does.

Five wrong answers, two real faults. What broke the run of them was never a better guess — it was a 5 KB failure small enough that no size story could explain it. The probe was worth building for that alone, even though its own first verdict was wrong.

The pictures are measurements

Both renderers draw every frame twice and compare the two passes. An image computed from fixed inputs must come out identical both times, so any pixel that differs is painted red and counted in the caption. It is the selfcheck idea made visible.

The tesseract answered a memory question directly: neither it nor a gyroid needs a stored 3D volume, so both fit in well under a megabyte. RAM was never the constraint — the ~14 KB-per-frame transport budget was, and there a wireframe on a flat field (which deflate loves, ~5 KB at full resolution) beats an organic gyroid cross-section (dense texture, would have been forced small and muddy). Measured, not assumed.

What the clean renders add up to

The fractal is floating point. The tesseract is floating-point geometry with integer line-drawing. Both come back with zero disagreements, run after run. Every clean render in an arithmetic domain other than 64-bit integer division tightens the case that the nondeterminism is exactly that narrow — which is both good news for most workloads and precise guidance for a fix.

Where it stands, and what is left honest

Two unikernels run live: the agent — chat, measured self-knowledge, semantic memory, web, reminders, fractal on demand — and a second instance animating the four-dimensional cross-section. Together they cost about a cent an hour. Everything is open source and committed with the reproducers alongside.

What is unfinished is stated plainly because the whole project runs on measured claims: the intermittent transport is mitigated by retries but not fixed, and the fix belongs to the platform; the arithmetic mechanism is isolated but not explained; and credential rotation on the keys used during the work is still outstanding. The one experiment that would turn the arithmetic finding into a headline — showing that RSA-CRT signing on a machine that faults one operation in four thousand becomes a self-inflicted private-key oracle, the classic Bellcore attack with no attacker — is designed and not yet run.
