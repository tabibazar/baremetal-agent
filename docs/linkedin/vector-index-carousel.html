A 16 MiB computer

Our AI agent was using 4% of its machine.

We gave it 59%. On purpose, and it made the thing genuinely better.

A vector database with no database under it — and no operating system either.

1 / 12

The machine in question

One program. No OS beneath it.

A Telegram agent compiled as a BareMetal unikernel: no kernel, no shell, no init, no container, no disk. A 2.9 MB image that boots straight into main().

Its memory ceiling is not a plan you upgrade. It is the platform maximum:

The problem worth solving

It could only find what you filed.

The agent remembers things you tell it. But recall was exact-key lookup — ask "what do you know about boot times?" and it found nothing, because you had filed it as "the unikernel starts in 31 ms".

The notes were there. The words were wrong.

3 / 12

What we built

Every memory, embedded, resident in RAM.

Each note is embedded once into a 768-dimension vector and kept in a static array. A question is embedded too, then compared against every resident vector.

One pass over an array. No tree. No index structure. No database. No disk — this machine has none of those things and now needs none of them.

Gotcha #1 — the silent one

Truncated embeddings are not unit vectors.

The model returns 3072 dimensions and truncates to 768 on request. We assumed the result was still unit length.

It isn't. Measured norm: 0.59.

Cosine over unnormalised vectors ranks LONGER notes above CLOSER ones. Silently. Plausibly. You would never catch it from the output.

7 / 12

Gotcha #2 — the boring one that matters

We parse 3,072 floats by hand.

There is no heap in this program. JSON goes through a fixed bump arena, and a batch of four embeddings would become 3,072 separate nodes in it.

So the embeddings are scanned out of the response with strtod. It costs nothing, and the shape is safe to assume — this program wrote the request.

8 / 12

The decision we are proudest of

1 in 4000

results on this platform come back wrong.

We had measured it that morning: this unikernel corrupts 64-bit arithmetic under load. A brute-force dot product over a big array is exactly that loop shape.

9 / 12

So we built it anyway

Because of how it fails, not whether.

A corrupted score reorders two neighbours in a ranked list. It cannot crash. It cannot invent a memory that was never stored.

A feature needing exact arithmetic would have been the wrong thing to put on this machine. The constraint picked the feature — not the other way round.

Know your platform's failure mode, then choose work that degrades instead of breaking.

10 / 12

Measure first, then claim

13 MiB boots. 14 does not.

Before writing a line of the feature, we probed the real ceiling: allocate X MiB, write every page, read it all back, see whether the machine survives.

Then sized the index to fit with margin, rather than guessing and finding out in production.

5 of 5 test queries return the note a human would pick. Search time over the index: 4.2 microseconds.
